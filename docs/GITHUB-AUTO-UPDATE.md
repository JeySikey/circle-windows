# GitHub Actions: создание и публикация самообновляющегося Circle Windows

## Шаг 1. Один раз создайте приватный ключ подписи (не включайте его в ZIP/Git)

На локальном компьютере с Python 3:

```powershell
python -m pip install cryptography
python tool/release_keys.py --generate --private-key circle-update-private.pem
```

Команда создаёт **приватный** PEM-файл. Содержимое файла целиком, включая строки `-----BEGIN PRIVATE KEY-----` и `-----END PRIVATE KEY-----`, вставьте в Github: **Settings → Secrets and variables → Actions → New repository secret** → имя **`CIRCLE_UPDATE_PRIVATE_KEY_PEM`**. Затем храните приватный PEM офлайн в безопасном месте. Никогда не коммитьте PEM. Не размещайте его на публичном сайте, в Issues, в артефактах или в репозитории. Публичный ключ GitHub Actions вычислит автоматически и вшьёт в собранный EXE.

Если при сборке секрет отсутствует, EXE соберётся, но **не сможет проверять доверенные обновления**. Установка секрета после сборки не исправит уже собранный EXE: сборку нужно повторить.

## Шаг 2. Первая сборка 0.5.0

Запустите `.github/workflows/windows.yml` через **Actions → Circle Windows build → Run workflow**. Установите созданный `Circle-Windows-Setup` на тестовый Windows 10/11 компьютер. Сохранится постоянный AppId для установки поверх 0.4.2, локальная авторизация защищена отдельно от бинарников.

## Шаг 3. Публикация подписанного релиза 0.5.0

Workflow автоматически выпускает GitHub Release для тега **`v0.5.0`**, если этот тег указывает на соответствующие исходники. Тег должен указывать на commit c версией `0.5.0` одновременно в `pubspec.yaml`, `lib/main.dart`, `.github/workflows/windows.yml` и `installer/Circle.iss`.

Для создания тега (в Git после commit):

```bash
git tag v0.5.0
git push origin v0.5.0
```

Убедитесь, что в Release опубликованы:

- `Circle_Windows_0.5.0_Setup.exe` — только для первой установки;
- `Circle_Windows_0.5.0_Payload.zip` — для будущих механизмов проверки и тестов;
- `update-manifest.json` — подписанный манифест ZIP.

Автообновление версии 0.5.0 на 0.5.0 не запускается — нужен более новый релиз.

## Шаг 4. Следующий выпуск 0.5.1 (уже без установщика у пользователя)

Обновите версию в `pubspec.yaml` (например `0.5.1+11`), `lib/main.dart` (`appVersion`), `installer/Circle.iss`, `build-installer.ps1`, `tool/validate_package.py` и `.github/workflows/windows.yml` (параметры Inno, payload, теги, подпись). Создайте commit и **`v0.5.1`**. Workflow загрузит три актива в новый GitHub Release.

Запустите старое приложение 0.5.0: оно проверит `releases/latest/download/update-manifest.json`, сверит Ed25519-подпись, покажет подтверждение и после согласия загрузит ZIP. Отдельный PowerShell-процесс дождётся завершения EXE, подменит каталог целиком и запустит новую версию. Повторный установщик не нужен.

## Безопасность и ограничения

- Публичный Release на GitHub, HTTPS, подписанный манифест и SHA-256 — обязательны. Неподписанные ZIP не устанавливаются.
- Приватный ключ при смене автоматически **не обновится** в старых клиентах; нужна предусмотренная процедура ротации ключа.
- Обновление заменяет **полный бинарный каталог** Flutter (EXE, DLL, плагины, data). Это не побайтный патч. Пользователь не переустанавливает программу, но размер скачивания соответствует текущей сборке.
- Встроенная система не меняет серверный PHP-код или пользовательские MySQL данные и не удаляет секреты из Windows secure storage.
- На Windows с жёсткими AppLocker/Defender/PowerShell-политиками сценарий может быть заблокирован; проверяйте лог. Для публичного релиза желательно подписать установщик и исполняемые файлы сертификатом подписи кода.
- Не модифицируйте в приложении доверенный публичный ключ из неавторизованных сетевых ответов.
- Запуск двух копий Circle одновременно может предотвратить обновление из-за блокировки DLL; убедитесь, что программа закрыта полностью.
